# 历史 Tab 重写需求

## 文档状态

- 状态：已实现，待评审
- 目标端：iOS SwiftUI，共享实现位于 `ChineseCalendarUI`
- 交互与 UI 基准：`Design/Prototype` 当前“朝代与年号流程重构”原型
- 数据基准：现有 SwiftData 朝代、正统期、皇帝、在位区间和年号模型

实现时必须打开当前 Web 原型，逐页参照其信息层级、卡片布局、内容密度、点击范围和导航关系。SwiftUI 使用系统原生的 `NavigationStack`、导航标题、Tab Bar 与 Safe Area，不机械复制网页的 CSS、固定像素或模拟状态栏。若原生控件约束导致表现不同，应优先保持相同的信息层级和交互语义，并在评审时说明差异。

## 背景

当前 SwiftUI 的历史 Tab 以“正统时间线”介绍卡和正统期列表为入口；朝代详情又把概况、边界比较和皇帝列表同时放在一个长页面中。信息层级偏重，用户不容易先理解一个朝代有哪些可继续查看的资料。

本次重写以朝代为入口，将朝代详情改成资料枢纽。用户先选朝代，再分别进入帝王、年号和朝代起讫三个分支。页面使用系统导航标题，不再用大型 Hero 卡片重复表达页面身份。

## 产品目标

1. 第二个 Tab 的用户可见名称改为“朝代”，内部 feature 仍可沿用 History 命名。
2. 默认按一条明确的正统传统展示朝代序列。
3. 朝代详情只承担分流，不在同一页堆叠完整帝王、年号和边界资料。
4. 帝王与年号分别使用稳定、可复用的领域卡片表达。
5. 正确区分朝代自称区间、正统期、皇帝在位区间和年号使用区间。
6. 页面、查询和领域组件放在共享 `ChineseCalendarUI` 中，本需求只要求完成 iOS 接入与验证。

## 非目标

- 不做通史、百科正文或无限扩展的历史事件流。
- 不做地图、人物关系图、朝代树或多种正统史观对照。
- 不把帝王、年号或浏览选择塞进 `CalendarRouter`。
- 不照搬 React 页面骨架，不新建通用 `SectionTitle`、`PageSummary`、`HistoryScreen` 或自定义导航栏。
- 本期不新增帝王详情的入口；现有 `EmperorDetailView` 可以保留，但不属于本流程的验收范围。
- 本期年号详情中的“所属皇帝”只展示信息，不继续 push 帝王详情。
- 不包含 macOS 根导航、窗口布局或 macOS App 验证。

## 术语与展示口径

### 正统期

首页展示的是默认 `OrthodoxTradition` 下的 `OrthodoxPeriod`，按 `sequenceIndex` 排序。朝代卡片上的年份来自该正统期的起止边界，不使用 `Dynasty.claimedStartDate` 和 `claimedEndDate` 替代。

例如清朝应在首页显示正统期 `1644—1912`；清政权自称起点等资料只在“朝代起讫”页对照展示。

网页原型中的唐、宋、元、明、清是交互与视觉样例。生产 SwiftUI 必须显示当前默认正统传统中所有可用记录，不得把这五条数据硬编码进 View。

### 国祚

朝代详情第三个入口和朝代起讫页使用“国祚”，不使用“跨度”，也不解释“首尾涉及多少个公历年份”。

当正统期的开始、结束边界都是可用的年精度索引时：

```text
国祚年数 = 结束边界年索引 - 开始边界年索引
```

因此明朝正统期 `1368—1644` 显示“国祚 276 年”，不做尾减首再加一。若当前精度不足以可靠计算，显示“国祚暂无”，入口仍可进入起讫页；不得猜测一个精确数字。

### 年号与在位区间

`EmperorReignSegment` 表示“谁在位”，`ReignEra` 表示“当时使用哪个年号”。二者是两条相关但不完全重合的时间线，UI 不得通过其中一条反推另一条。

年号和在位区间使用半开区间 `[start, end)` 存储。对年精度数据，面向用户的使用年份需要将 exclusive end 转成最后一个实际使用年。例如 `[1403, 1425)` 显示为 `1403—1424`；`[1425, 1426)` 显示为 `1425`。

正统期页面展示的是两个政治交接边界，如 `1368—1644`；它与年号列表的“实际使用年份”不是同一个格式化语义，不得共用一个简单的通用年份范围函数。

### 日期精度

任何年、月、日、范围或未知精度都必须保留。只能确定到年时显示“年精度”，不得补成正月初一或具体月日。精度不足时优先显示可理解的来源文本或“时间待考”，不制造精度。

## 信息架构

本流程包含 6 个具有独立导航身份的 Screen：

```text
朝代目录
└── 朝代详情
    ├── 帝王列表
    ├── 年号列表
    │   └── 年号详情
    └── 朝代起讫
```

加载中、空数据、部分字段缺失和滚动位置都是 Screen State，不新增路由页面。卡片的普通、按下、不可用等表现属于 Component State。

## 页面需求

### 1. 朝代目录

导航身份：历史/朝代 Tab 根页面。

页面要求：

- 使用系统导航标题“朝代”；iOS 根页面允许 large title，但内容区不再重复大型标题卡。
- 标题下可以保留一行普通说明：“沿正统时间线，进入一个朝代的纪年体系”，不得放进卡片。
- 列表按默认正统传统的 `OrthodoxPeriod.sequenceIndex` 排序。
- 每条使用 `DynastyCard`，显示朝代名、正统期起止边界、皇帝数和年号数。
- 点击一条记录 push 对应朝代详情。
- 若 `OrthodoxPeriod.dynasty` 缺失，仍显示时期名称和边界，但不伪造统计数；该条不可进入朝代详情并说明“资料暂缺”。
- 同一朝代在同一正统传统中有多个时期时，按正统期分别显示，不能按 `dynastyID` 静默合并。

明朝样例：

```text
明
1368—1644
16 位皇帝 · 17 个年号
```

### 2. 朝代详情

导航身份：由朝代目录 push 的资料枢纽。

页面要求：

- 使用 inline 系统导航标题，例如“明”；返回按钮标题为“朝代”。
- 不显示朝代 Hero 卡，不在正文重复页面标题。
- 顶部只显示三个同级、可点击的 `DynastyFactCard`：
  - `16 位皇帝`
  - `17 个年号`
  - `276 年`
- 卡片只显示数值、单位和 chevron，不显示“按即位顺序”“完整时间线”“正统国祚”等小标题。
- 三个入口分别 push 帝王列表、年号列表和朝代起讫。
- 若存在能解释统计关系的短说明，可在卡片下以一行普通文字展示，不使用独立卡片。例如：“明英宗两度在位，因此 16 位皇帝对应 17 个年号。”
- 页面不直接展开完整帝王列表、年号列表或边界比较。

进入本页时必须保留来源 `orthodoxPeriodID`，因为 `dynastyID` 本身不能唯一表示同一正统传统中的某一段正统期。

### 3. 帝王列表

导航身份：由朝代详情的“位皇帝”入口 push。

页面要求：

- 系统导航标题“帝王”；返回按钮标题为朝代短名，例如“明”。
- 列表顶部只保留一行摘要，例如“16 位皇帝 · 17 段纪年”，不使用总结卡。
- 皇帝按 `Emperor.sequenceIndex` 排序，不从年号顺序或在位区间去重结果反推。
- 每位皇帝使用 `EmperorCard`，显示：
  - 序号；
  - 主要显示名；
  - 庙号，缺失时可降级为其他可靠称号；
  - 一段或多段在位年份；
  - 可可靠获得时的在位时长；
  - 所属年号标签；
  - 必要的简短说明。
- 多次在位的同一皇帝只显示一张卡；多个 `EmperorReignSegment` 依 `segmentIndex` 排列，并完整表达多个区间。
- 本期 `EmperorCard` 是展示组件，不显示 chevron，也不进入帝王详情。

### 4. 年号列表

导航身份：由朝代详情的“个年号”入口 push。

页面要求：

- 系统导航标题“年号”；返回按钮标题为朝代短名。
- 顶部只保留一行摘要，例如“17 个年号 · 1368—1644”，不使用总结卡。
- 年号通过 `ReignEra.emperor.dynasty` 筛选，并严格按 `ReignEra.sequenceIndex` 排序；不得按皇帝列表顺序拼接。
- 每条使用 `ReignEraCard`，显示年号使用年份、年号名、使用时长、所属皇帝和可靠称号。
- 每张年号卡均可点击并 push 对应年号详情；不得只让原型中的“永乐”可点击。
- 同名年号使用稳定 `ReignEra.id` 区分，不能按名称默认取第一条。

### 5. 朝代起讫

导航身份：由朝代详情的“年”入口 push。

页面要求：

- 系统导航标题“朝代起讫”；返回按钮标题为朝代短名。
- 顶部使用普通摘要，不使用 Hero 卡：朝代名与“正统时间线”、正统期起止边界、国祚年数。
- “朝代自称与正统期”并排或分行对照：
  - 朝代自称来自 `Dynasty.claimedStartDate` 与 `claimedEndDate`；
  - 正统时间线来自当前 `OrthodoxPeriod.startBoundary` 与 `endBoundary`。
- 两行只显示标签和主要时间，不再添加“开始、结束均为年精度”“本原型采用的正统叙事”等重复副标题。
- “关键边界事件”只收录与建立、正统交接、改元中断、灭亡或范围口径直接相关的少量事件，不扩展成通史。
- 底部可以展示一条范围说明，例如“南明与明郑不计入明朝正统期”；它必须来自数据或展示模型，不能硬编码在 View 中。
- 页面不显示国祚计算公式，也不解释“跨度”或“涉及多少个公历年份”。

### 6. 年号详情

导航身份：由年号列表中的 `ReignEraCard` push。

页面要求：

- 系统导航标题为年号名，例如“永乐”；返回按钮标题为“年号”。
- 顶部普通摘要显示朝代、该年号在朝代时间线中的序号、使用年份和时长。
- “所属皇帝”卡显示皇帝主要显示名和可靠称号；本期仅展示，不继续导航。
- “纪年边界”分别显示开始和结束表达及各自精度。
- “年号交接”显示 `ReignEra.note` 中与沿用、改元或中止有关的说明。
- 不显示重复的“资料口径”卡；不把年精度补成具体日期。
- 字段缺失时隐藏对应次要内容，不显示空白标签或由 View 猜测的文字。

## 导航关系

所有关系都使用系统 `NavigationStack` 的 push/pop 语义：

| # | 来源 | 真实触发控件 | 目标 | 语义 |
|---|---|---|---|---|
| 1 | 朝代目录 | `DynastyCard` | 朝代详情 | push |
| 2 | 朝代详情 | 返回“朝代” | 朝代目录 | pop |
| 3 | 朝代详情 | `位皇帝` 的 `DynastyFactCard` | 帝王列表 | push |
| 4 | 帝王列表 | 返回朝代短名 | 朝代详情 | pop |
| 5 | 朝代详情 | `个年号` 的 `DynastyFactCard` | 年号列表 | push |
| 6 | 年号列表 | 返回朝代短名 | 朝代详情 | pop |
| 7 | 朝代详情 | `年` 的 `DynastyFactCard` | 朝代起讫 | push |
| 8 | 朝代起讫 | 返回朝代短名 | 朝代详情 | pop |
| 9 | 年号列表 | `ReignEraCard` | 年号详情 | push |
| 10 | 年号详情 | 返回“年号” | 年号列表 | pop |

系统边缘返回手势、工具栏返回按钮和导航状态恢复应得到同样结果。切换到其他 Tab 再返回时，沿用当前 `NavigationCore` 的既有 path 行为，不为本功能另建导航状态源。

建议路由至少能表达以下目的地身份，实际枚举命名可在实现时调整：

```swift
dynasty(orthodoxPeriodID: String)
emperorList(dynastyID: String)
reignEraList(dynastyID: String)
dynastySpan(orthodoxPeriodID: String)
reignEra(reignEraID: String)
```

Router 只保存“去哪个 Screen”的稳定 ID 和导航结构。已加载的 `Dynasty`、`Emperor`、`ReignEra` 数组、滚动位置、格式化文本或卡片展开状态不进入 Router。

## SwiftUI 领域组件

本次只沉淀具有历史业务语义的组件：

| 组件 | 必要输入 | 行为边界 |
|---|---|---|
| `DynastyCard` | 朝代名、正统边界文本、皇帝数、年号数 | 整张卡作为一个导航入口，不自行查询数据 |
| `DynastyFactCard` | 数值、单位、无障碍标签、目标或 action | 只表达朝代资料分支，不承担通用统计卡职责 |
| `EmperorCard` | 序号、姓名/称号、在位区间、时长、年号、说明 | 纯展示；不持有 Router，不自行查询 SwiftData |
| `ReignEraCard` | 年号、使用区间、时长、皇帝信息、目标或 action | 整张卡可点击；不按皇帝顺序推导自身顺序 |

页面使用 SwiftUI 原生 `NavigationStack`、`navigationTitle`、`ScrollView`/`List`、`LazyVStack` 和普通标题排版。章节标题、页面摘要、导航栏和 TabView 不为了与 TypeScript 同名而包装成项目组件。

TypeScript 与 SwiftUI 不共享源码；两端对齐的是组件职责、输入字段、信息层级和交互语义。SwiftUI 组件应接收领域对象或只读展示模型，避免接收不断增长的零散字符串参数。

## 数据与展示模型要求

### 现有数据可直接支持

- `OrthodoxTradition`、`OrthodoxPeriod`、`OrthodoxBoundary`：首页排序、正统期和正统边界。
- `Dynasty`：朝代名称、自称边界、皇帝关系和说明。
- `Emperor`：人物身份、称号、默认展示顺序和年号关系。
- `EmperorReignSegment`：一次或多次在位区间。
- `ReignEra`：年号身份、所属皇帝、朝代时间线顺序、使用区间和交接说明。
- `ChineseDateExpression`：时间原文、结构化索引与精度。

### 实施前需要补齐或明确的数据

1. **使用时长文本**：当前年精度边界可以计算整数年，但“约四个月”等来源时长不能从现有索引可靠恢复。导入层或展示模型必须提供权威的可选时长文本；没有时宁可隐藏，不从复合 `sourceText` 在 View 中临时解析。
2. **关键边界事件**：当前持久化模型没有独立事件实体。若要完整实现原型中的事件时间线，应由导入数据或只读 repository 提供稳定结构，至少包含 `id`、`orthodoxPeriodID`、时间表达、标题、说明和排序。不得在 SwiftUI 中写死明朝事件数组。
3. **统计关系说明**：类似“明英宗两度在位”的一句话应来自领域说明或专用展示元数据，不根据数量差在 View 中自动编造原因。
4. **默认正统传统**：查询层必须明确首版使用的 `OrthodoxTradition.id`，不能依赖 fetch 返回的第一条记录。

建议在页面与 SwiftData 对象之间建立只读展示模型/formatter，统一生成正统边界、实际使用年份、时长和精度文案。卡片只负责渲染，不负责理解半开区间。

## 页面状态与异常处理

- 根页面没有正统期：使用 `ContentUnavailableView`，说明当前 store 没有可显示的正统时间线。
- 路由 ID 找不到对象：当前 Screen 显示对应的“没有找到朝代/年号”空态，不自动 pop 到其他页面。
- 朝代存在但皇帝或年号为空：对应入口显示 `0`，进入后显示明确空态。
- 单条记录缺少可选字段：保留卡片并隐藏缺失的次要字段，不删除整个列表项。
- 只有 source text、无法结构化日期：显示来源文本和“精度未知”；不显示推算时长。
- 数据加载和格式化错误不得让一个坏记录阻止其他记录显示。

## iOS 与可访问性

### iOS

- 第二个 Tab 使用标题“朝代”，保留独立 `NavigationStack` 和 `historyPath`。
- 根页面使用系统 large title，详情页使用 inline title。
- Tab Bar、Safe Area 和系统返回手势按系统行为处理，不在共享页面内模拟网页原型的底栏或状态栏。

### 可访问性

- Dynamic Type 放大后数值、单位和 chevron 不重叠；卡片允许纵向增长，不固定正文高度。
- 每个可点击卡片只有一个清晰的无障碍元素和动作。
- `DynastyFactCard` 的 VoiceOver 文案使用完整动作，例如“查看明朝 16 位皇帝”。
- `ReignEraCard` 至少读出年号、使用年份、所属皇帝和“按钮”。
- 时间线的颜色和线条不是唯一的信息载体。
- 深色模式、Increase Contrast 和 Reduce Motion 下保持可读；本流程不依赖自定义动画完成导航。

## 验收标准

### 功能

- 能从朝代目录进入任一有数据的朝代详情。
- 朝代详情的三个资料入口均可点击，并进入正确的独立 Screen。
- 年号列表中的每一项都能进入与其稳定 ID 对应的年号详情。
- 10 条 push/pop 关系均按上表工作，返回后保留上一页合理的滚动位置。
- 皇帝和年号排序分别使用各自领域排序字段；明英宗只出现一张帝王卡，正统与天顺仍处于正确的年号位置。
- 清朝首页正统期显示 `1644—1912`，朝代起讫页能同时表达其自称边界和正统边界。
- 明朝正统期 `1368—1644` 显示“国祚 276 年”，界面不出现“跨度 276 年”或“涉及 277 个公历年份”。

### 视觉

- 所有 Screen 仅用导航标题表达页面身份，不出现旧版大型 Hero 标题卡。
- 朝代详情只保留三个无小标题的资料入口和必要的一行说明。
- 帝王、年号列表顶部总结是普通单行文本，不是独立卡片。
- 朝代起讫对照行不包含重复副标题；年号详情不包含资料口径卡。
- 实现评审时逐页对照当前 Web 原型；常规与紧凑宽度、浅色与深色下保持相同的信息层级、卡片关系、内容密度和点击范围。
- Web 原型中的固定设备边框、状态栏和自绘 Tab Bar 不作为 SwiftUI 像素级复制目标，iOS 系统控件产生的合理差异可以接受。

### 工程质量

- 生产数据不引用 `Design/Prototype/src/screens/historyData.ts`，SwiftUI View 中没有明朝专用数组或按名称分支。
