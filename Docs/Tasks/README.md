# 任务方案与结果记录

为会影响后续开发的任务保留目标、决策理由和验收证据，供实现和 review 共用。记录使用中文，代码标识符保留原名。

## 何时创建

- 重要功能、跨模块状态或导航调整、数据迁移，以及根因或修复方案会影响后续设计的复杂问题，需要留下记录。
- 文案、间距、注释、格式等小改动，以及普通调查、单纯 review 和文档整理，通常在现有 Issue / PR 或审查报告中说明即可，不因耗时长或有 Issue 编号就创建目录。
- 用户明确要求时可以创建。判断依据是未来维护者是否需要了解这次设计选择，而不是改动行数。

已有方案或验证文档可以继续使用并相互链接。需要补录历史任务时标明是回溯记录，不把事后整理写成实现前已确定的方案。

## 目录与文件

以 Issue 为主要入口时使用以下结构。尖括号为命名示意，不创建占位目录：

```text
Docs/Tasks/issue-<number>-<slug>/
  000-plan.md
  001-result.md
```

- `number` 使用真实 GitHub Issue 编号，`slug` 使用简短的英文连字符主题名。没有 Issue 时使用 `task-<YYYY-MM-DD>-<slug>/`，不虚构编号。
- 先搜索相关文档；一个设计跨多个 Issue 或 PR 时复用同一目录，在文档中关联各项，避免复制方案。
- `000-plan.md` 在实现前写；`001-result.md` 在有实际实现或验证结果后写，并随交付更新。需要保留关键证据时再创建 `evidence/`。
- 同一设计内的重要后续补充按需添加 `002-<topic>.md`，并从方案和结果链接过去。根本改变设计时新建记录，双向链接并标明原方案已被替代。

## 编写与审查流程

1. **先明确方案。** 调查现有代码和需求，写清目标、范围、选择理由及可检查的验收标准。已有明确需求和授权时继续实现；会改变目标、范围或验收且无法从现有信息确定的决策，需要澄清。草案中的待定想法不作为已接受要求。
2. **按同一依据实现。** 引用 [通用规范](../Conventions/Common.md)、[SwiftUI 规范](../Conventions/SwiftUI.md) 和相关领域文档，不在每个任务目录复制编码规则。发生有意义的方案调整时记录原因及决策依据，保留原来的选择背景，不通过改写验收标准掩盖未完成项。
3. **审查读取方案。** 将相关方案、已接受的补充和验收标准交给 reviewer，对照实际代码与证据核验。每个验收项在结果中标明已验证、未验证、失败或不适用及理由；未确定是否适用时保持未验证。
4. **汇总实际结果。** 在实现与审查共同进行的任务中，由主 Agent 把确认的问题处理结果、方案偏差和验证缺口整理进 `001-result.md`。专项 reviewer 只写自己的报告。单独请求 review 时，在审查汇总中列出与方案及验收标准的核对结果；除非任务包含文档维护，否则不修改受版本控制的任务记录。

审查分工、证据规则与复审停止条件统一遵循 [review-changes](../../.agents/skills/review-changes/SKILL.zh-CN.md)。不因创建了任务记录就自动启动一次审查。

## 证据与记录边界

- 方案和精简后的结果作为项目文档随相关改动交付。文档要区分当前事实、待实现方案和待验证假设；实际代码路径须核实，计划新增的路径明确标注为拟新增。
- 验证结果关联实际检查的 commit 或可识别的工作区快照，并记录工具或命令、环境、结果及必要证据。仅有 HEAD 不能代表带未提交改动的工作区；复用旧证据时说明适用的代码状态。
- 区分源码检查、构建、测试、Preview、Simulator 交互和真机验证。实现完成不等于全部验收通过；报告未运行、失败和环境阻碍。
- 每轮专项报告和临时输出继续放在已忽略的 `.output/reviews/`。长期需要的关键截图或必要日志摘录放入任务目录的 `evidence/`，或引用可持续访问的 PR 附件；不能只用本机临时路径作为长期证据。
- 结果保留重要问题的 ID、处理状态、理由和剩余决策。只保留可核查的结论，不复制完整对话、每次命令输出或每轮审查全文。
- 文档记录不代替 GitHub Issue / PR 的状态。现有授权范围决定是否提交、发布或更新远程内容。

## 最小模板

按任务合并或删去不适用的小节，不为填充模板制造内容。

### 000-plan.md

```markdown
# <任务标题>：方案

- 关联：真实 Issue、PR 和已有领域／设计文档
- 状态：草案 / 可执行 / 已替代（附后续方案链接）
- 更新日期：YYYY-MM-DD

## 背景、目标与范围

当前问题、预期行为，以及明确不做的事情。

## 方案与决策

涉及的模块、关键行为、备选方案、选择理由及决策依据。

## 验收标准

| ID | 场景与预期行为 | 验证方式 |
| --- | --- | --- |
| AC-01 | 可观察的结果或必须保持的约束 | 针对性测试／交互步骤等 |

## 待定事项与后续调整

尚未确定的决策；后续调整记录日期、原因和相关链接。
```

### 001-result.md

```markdown
# <任务标题>：结果

- 方案：000-plan.md
- 关联：真实 Issue / PR
- 记录日期：YYYY-MM-DD
- 代码状态：commit 或工作区快照；实现完成情况

## 实际结果与方案偏差

实际行为、关键代码位置，以及与原方案不一致的地方和原因。

## 验收证据

| 验收项 | 状态 | 工具／命令、环境、代码版本与证据 |
| --- | --- | --- |
| AC-01 | 已验证 / 未验证 / 失败 / 不适用 | 实际结果、证据链接或未完成原因 |

## 审查结论与剩余事项

审查的代码状态、覆盖边界；重要问题 ID、处理结果及理由；未完成验收和待决定事项。未运行 review 时如实说明。
```

参考：[OneV：代码审核](https://onevcat.com/2026/10/agent-review/)中的方案与结果记录做法。本项目按任务的重要性采用，不要求每个 Issue 建目录，也不固定审查轮数。
