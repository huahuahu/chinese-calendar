# 改动审查 · 中文对照版

本文件供维护者阅读，与 [英文执行版 SKILL.md](SKILL.md) 使用相同的章节编号和规则 ID。修改时同步维护两份；Agent 执行时只需加载英文版。

技能名：`review-changes`。用于按指定范围审查 Chinese-date 的代码改动或 PR，通过专项子 Agent、证据验证、去重和各 Agent 的报告文件完成审查。适用于用户要求的代码 review 和合并前 review；普通实现任务或讨论 review 规范不会触发一次审查。

## 1. 目标与边界

发现指定改动中值得处理的问题，减少误报、重复反馈和反复修改。审查约定的范围，不默认扩展到整个仓库。

可用时，使用专项子 Agent 执行能够独立进行的审查。遵循项目对模型的要求：使用可用的最强推理模型，不悄悄换成较小的模型。根据改动和并发额度决定分工数量；小改动可能只需要一个专项 Agent。无法委派时，顺序执行各项审查，并说明这一限制。

专项 Reviewer 检查产品代码，只写分配给自己的报告。本技能本身不授权修改产品代码、提交 commit、发表评论、请求远程 review、推送或合并；用户已经单独给予的授权仍然有效。使用子 Agent 工具完成分工，不为此新建用户侧的独立聊天。

Agent 指令和专项报告使用英文。最终的 `summary.md` 和对用户的回复使用中文，称呼用户为“花花虎”。用户明确指定其他语言时，遵循用户要求。

## 2. 共用规则来源

编写代码和审查代码使用同一套项目规则。本技能只定义审查流程，不另造一套编码规范。

读取适用的 `AGENTS.md`、需求和验收标准。根据改动需要加载其他来源：

| 来源，路径相对于仓库根目录 | 何时读取 |
| --- | --- |
| `Docs/README.md` | 查找与本次改动相关的项目规范，只加载适用专题 |
| `Docs/Tasks/README.md` 和相关既有任务记录 | 重要功能、影响后续设计的修复，或已有方案记录的改动；已接受的决策、验收标准和实现证据 |
| `CONTEXT.md` 和 `Docs/` 中相关领域文档 | 领域术语、日历行为、模型边界和已接受的设计决策 |
| `Docs/Conventions/Common.md` | 编写或审查代码时；注释和日志等共用规范 |
| `Docs/Conventions/SwiftUI.md` | 编写或审查 SwiftUI 时；View 拆分和展示常量的项目规则 |
| `.agents/skills/swiftui-pro/SKILL.md` | 编写或审查 SwiftUI 时 |
| `.agents/skills/swiftdata-pro/SKILL.md` | 涉及 SwiftData 模型、关系、查询或存储时 |
| `.agents/skills/swift-concurrency-pro/SKILL.md` | 涉及隔离、任务生命周期、取消和异步状态更新时 |
| `.xcodebuildmcp/config.yaml` 和仓库的 Xcode 约定 | 执行构建、测试、Preview 或 Simulator 操作前 |

用户当前的要求优先于本地指导；项目规范与通用技能建议不一致时，遵循项目规范。区分强制规则、偏好和建议。报告违反规则时，引用准确的适用条款，并解释为什么满足其适用条件。核实被引用的文件和 API，名称本身不构成证据。要求中出现未知文件时，先确认文件，再执行该规则。

## 3. 确定范围并创建记录

委派之前，主 Agent 记录：

- 用户请求、验收标准（有 ID 时保留）、相关方案及已接受的补充、纳入的路径和排除项。不把草案中的想法当作已接受要求，也不为执行 review 而补造实现前的方案。
- 仓库根目录、比较方式、适用时解析出的基准和当前 commit ID，以及未提交和未跟踪文件状态。PR review 使用该 PR 实际的 base 和 head，并记录 diff 使用的 merge base；不能从当前分支名猜测 PR 目标。
- 对工作区审查，记录相关已暂存和未暂存 diff，以及纳入范围的未跟踪文件内容或哈希。保留用户文件，不为获得干净环境而提交、stash 或 reset。
- 适用规则来源、专项分工、报告路径，以及已有验证证据和它对应的代码版本。

目标不明确时，先检查本地状态。如果存在明确的当前改动，就说明范围并使用它；否则问一个简短问题。工作区干净且没有明确比较目标，不代表可以开始全项目审计。

在 `.output/reviews/<run-id>/round-01/` 下创建唯一目录。仓库已经忽略 `.output/`。用户指定了输出目录时使用该目录。不覆盖其他运行或轮次的记录。

```text
context.md
reports/
  domain.md
  ui.md
  data-concurrency.md
summary.md
```

只为选中的分工创建报告文件。在 `context.md` 记录跳过的分工和原因。每轮审查的过程产物不纳入产品 diff。报告绑定记录的代码状态，发布汇总前重新检查状态。审查期间代码发生变化时，找出受影响的问题并针对新状态复核，或明确标记审查已过期；不能悄悄混用不同版本。

## 4. 分派独立的专项 Agent

按 diff 中的风险选择分工。以下是起点，不要求每次全部启动：

| 分工 | 职责 | 可用专项指导 |
| --- | --- | --- |
| `domain` | 需求符合性、日历与日期边界、状态归属、导航、数据不可用行为和调用方契约 | `CONTEXT.md` 和相关领域文档 |
| `ui` | SwiftUI 状态传递、展示、可访问性、布局，以及视觉和交互证据的覆盖边界 | `swiftui-pro` |
| `data-concurrency` | 按需检查 SwiftData 关系或迁移、持久化、下载、隔离、取消和资源生命周期 | `swiftdata-pro` 和／或 `swift-concurrency-pro` |

较大的分工包含独立风险时可以拆开；脚本、构建配置或文档改动可以使用更适合的分工。日志等跨模块规则，交给负责相应改动的 Agent 检查。各分工使用同一份规则来源。

向每个专项 Agent 提供记录好的范围、代码状态、相关规则路径、职责和独占的报告路径，同时提供下方 R1–R10 及报告格式。允许追踪改动行之外的调用方和依赖，但每个问题都要说明与本次改动的关联。首轮独立检查前，不把其他 reviewer 的结论当作预设答案传给它。

共享的构建、测试和 Simulator 操作由主 Agent 协调。专项 Agent 提出针对性的验证请求，或使用已记录的证据，不能争用同一个 Xcode 会话或设备。文档或低影响改动不运行无关的完整测试套件；需要验证时遵循仓库的工具顺序和环境约定。

等待全部已分派工作完成，或明确记录为未完成。报告缺失、工具失败、运行环境不可用，都不等于审查通过。

## 5. 问题报告规则

- **R1 — 证据：** 说明实际可达的触发条件、预期与实际行为或明确的规则差异、实际影响，以及准确源码位置。真实调用链分析可以证明问题；复现很有价值，但不强求每个静态可证明的缺陷都运行复现。
- **R2 — 反证：** 检查周边代码、调用方、保护条件、支持的版本和适用例外。API 行为会影响结论时，使用仓库要求的文档工具核实。仅凭名称、直觉或置信度分数不能成立。
- **R3 — 改动归因：** 区分本次引入、加重和原有问题。无关的原有问题不进入本次必须修复列表；如果改动让旧问题变得可触发，要解释清楚。
- **R4 — 不凑数：** 零问题是有效结果。不为填充分工而制造问题。未解决的假设放到验证缺口中，不当作已确认缺陷。
- **R5 — 规则与偏好：** 要求遵守规范时，引用强制性的项目条款。默认省略个人对命名、风格或抽象方式的偏好；只有用户要求时才列可选建议。不把风格偏好描述成功能缺陷。
- **R6 — 工具覆盖：** 使用 formatter、lint、编译器和测试结果作为证据，不把工具的每条诊断重复包装成 AI 发现。必需检查失败或未运行，仍须出现在验证状态中，不能隐去。
- **R7 — 严重程度：** P0 是极少见且已证明的重大故障；P1 需要优先修正；P2 是应在正常开发中修复的实际缺陷；P3 是可选完善。影响程度与确定性分开判断。违反强制规范可以需要修正，但不等于运行时 bug。单纯缺少测试属于覆盖缺口，除非已接受的需求明确要求该测试。
- **R8 — 去重：** 同一根因最终只保留一个问题，即使多个 Agent 都发现它。保留贡献报告的 ID 和相关位置。用证据解决相互矛盾的报告，不用多数投票决定。
- **R9 — 限定建议：** 说明修复至少需要恢复的行为或约束。局部修复能满足要求时，不要求大规模重写。Reviewer 在审查过程中不修改产品代码。
- **R10 — 如实验证：** 区分源码检查、构建、测试、Preview、Simulator 交互和真机检查。编译或 Preview 渲染不能证明实际交互正确。未完成的验收检查列为缺口，不悄悄免除，也不宣称改动已经完整验收。

## 6. 报告格式与主 Agent 验证

每个专项 Agent 都写英文 Markdown 报告，零问题时也包含这些字段：

这些是必需的信息，不要求每个字段单独占一个标题。共用的快照信息和测试输出可以链接 `context.md` 及共享检查产物，避免在报告各处重复。零问题报告使用简洁的元信息、简短且有证据的判断依据和覆盖边界，不重述全部规则。

| 英文字段 | 中文含义 |
| --- | --- |
| Lane / assigned scope | 分工及分配的范围 |
| Reviewed base/head or working-tree snapshot | 审查的基准、当前版本或工作区快照 |
| Status: complete / incomplete / stale | 完成／未完成／已过期 |
| Rule sources read | 已读取的规则来源 |
| Paths and execution paths inspected | 已检查的文件及执行路径 |
| Checks performed and results; checks not performed | 已执行检查及结果、未执行检查 |
| Findings | 发现的问题，使用下表格式 |
| Verification gaps and coverage limits | 验证缺口与覆盖边界 |

| 单个问题的英文字段 | 中文含义 |
| --- | --- |
| ID: `<lane>-001` | 稳定的问题 ID |
| Kind: defect / mandatory-rule / optional | 缺陷／强制规则／可选建议 |
| Priority: P0 / P1 / P2 / P3 | 优先级 |
| Location | 相对于仓库的文件路径和对应审查版本的行号 |
| Trigger and expected/actual behavior | 触发条件和预期／实际行为 |
| Impact | 影响 |
| Evidence and counterevidence checked | 证据及已检查的反证 |
| Applicable rule citation, if any | 适用时引用具体规则 |
| Change attribution: introduced / worsened / pre-existing | 本次引入／加重／原有问题 |
| Verification: code-traced / reproduced / unverified | 调用链已核实／已复现／未验证 |
| Minimal correction goal | 最小修正目标 |

未验证的候选问题放在缺口部分。报告保留结论和可检查的证据，不要求记录隐藏的思考过程。同一问题在后续轮次沿用稳定 ID。

主 Agent 读取每份报告，对照源码或相关测试证据检查候选问题，按根因去重。问题有争议或影响较大时，可在有实际价值的情况下委派
针对性的验证 Agent，让它尝试证实或推翻该问题，并写独立报告。另一个 Agent 表示同意，但没有证据，不能算确认。

生成中文 `summary.md`，包含：

- 审查范围、代码状态及各分工的完成状态。
- 按影响排序的已确认问题，附 ID、源码位置、证据和最小修正目标。
- 清楚区分必须修正、用户要求的可选建议和验证缺口。流程或强制规范问题与功能缺陷分开表达。
- 处理记录：`open`（待处理）、`fixed-and-verified`（已修复并验证）、`rejected`（不成立）或 `deferred`（延期），记录原因和对应专项报告 ID。不成立的判断需要反证；延期要记录由谁接受剩余风险，或说明决策仍待定。不替用户免除要求。
- 与已接受方案的符合情况、偏差、验证范围和未完成的验收标准；已有验收项 ID 时沿用。没有确认问题时，表述为“在本次审查范围内未发现值得处理的问题”，仍保留覆盖边界。

任务包含实现或任务记录维护时，主 Agent 还应按 `Docs/Tasks/README.md`，把已核实的结论和持久证据整理到关联的 `001-result.md`。单独请求 review 时，在 `summary.md` 中报告上述核对结果，不修改受版本控制的任务记录。专项 Agent 仍只写分配给自己的报告。

## 7. 复审与停止条件

得到独立授权的修复完成后，在同一次运行下创建 `round-02/` 等新轮次，记录新代码状态并保留旧报告。复查未解决问题，同时将修复 diff 当作新代码检查，沿受影响的执行路径查找回归，不只确认上一轮问题是否消失。需求大幅变化或范围扩展到无关内容时，另开一次运行。

没有新证据，不重新打开已否定或已修复的问题。首轮后不新增可选润色建议；新发现的实质缺陷或强制规则违反仍要报告，并解释适用原因。不固定最低审查轮数。再次全面审查需要理由，例如架构变化或新增受影响子系统。

指定分工均已交代清楚、确认问题及缺口已报告时，本次审查结束。如果任务同时包含审查和修复，则在必须修复的问题及相关验证完成后结束，或准确报告剩余阻碍。不为了得到空列表而反复执行全面审查。一次针对性验证后仍无法确定的问题，记录缺失的证据或需要的决策并交回，不让 Agent 无限循环。

## 8. 维护本技能

项目编码规范统一放在 `Docs/Conventions/`，并由 `Docs/README.md` 索引。简短的通用规则集中在 `Common.md`；SwiftUI 等需要详细说明的专题单独成文。新增已接受的规则时，在对应文档中写清适用范围、要求的行为、例外和验证方式，并确保 `AGENTS.md` 指引实现与审查读取。模块 README 和技能只链接到这个统一来源，不重复维护规则。这里只维护 review 的组织方式。重复出现的反馈，得到维护者接受后才升级为项目规则。

同时更新本文件和 `SKILL.md`，保持章节编号与规则 ID 对应。使用有代表性的 diff 验证调整，包含零问题案例；观察误报、重复问题和修改轮数，不用问题数量评价效果。
